Spare capacity before the drain.

Eviction Guard scales opted-in Deployments so replacement pods are Ready, then holds voluntary eviction until they are. One at-risk pod at a time, then it scales back.

What happens on a drain

  1. Signal

    A Karpenter taint, cordon, or cloud notice matches a policy.

  2. Scale spare

    Opted-in Deployments gain pods that are Ready off the dying node.

  3. Hold eviction

    The webhook denies pods/eviction until that spare is Ready, then allows one at-risk pod.

  4. Scale back

    After a cooldown, capacity returns to baseline and the window closes.

Where this fits

MechanismWhat it guaranteesWhat it leaves open
PodDisruptionBudget A floor of replicas survives No spare. The replacement starts cold.
HorizontalPodAutoscaler Scale follows load It reacts after the error spike.
Eviction Guard Warm spare before eviction. The webhook sequences the drain. Voluntary eviction only. Node disruption, not a crash.

Opt-in, not a lock

eviction-guard.io/protected: "true" on the pod template does not block eviction. The webhook does, and only for workloads that also set eviction-guard.io/scale-backend.

What it will not do

  • Replace per-app PodDisruptionBudgets
  • Protect against node crash, OOM, or a network partition
  • Schedule or place pods
  • See kubectl delete pod — that bypasses the Eviction API
